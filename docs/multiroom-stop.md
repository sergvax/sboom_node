# Как распускается нативный мультирум и почему это занимает ~12 секунд

## Суть

Группу SberCast создаёт и распускает **прошивка колонки**, не приложение. Локальной
команды «выйти из группы» на порту 20000 нет:

- `MediaCommand` (op=16) заканчивается на `REMOVE_DISLIKE = 15`. Команды
  `STOP_MULTIROOM` в enum не существует — `field(3, 2, Empty)` прошивка
  молча игнорирует (это видно по generic-ACK без изменения состояний).
- Единственный корректный по protobuf-схеме стоп — StarCommand 140
  (`multi_room_message` → `MultiRoomCommand.stop_multiroom = Empty`). На
  живых SberBoom 1.104.35, SberPortal 1.102.34 и SberBoom Mini 2 1.104.35 он
  принимается (ACK), но группу не распускает: роли `MASTER`/`SLAVE` держатся.
- Перебор `op=16` с командами 1..40 на живой группе: везде generic-ACK,
  состояние не меняется.
- `START_MULTIROOM` с ведомой колонки (cmd=8) — ACK, состав группы не меняется.
- Запуск отдельного трека на ведомой (deeplink) — трек остаётся мастерским,
  ведомая не «отцепляется».
- `mute`/`unmute` (cmd 0/1) работают по каждой колонке, но группу не распускают.
- `seek` в конец трека, `pause`+`play` через 2 с, пауза+повторная пауза — группу
  не распускают.

Роспуск происходит по таймеру прошивки: `multiroom.turnOffMultiroomAfterPauseMs`
(дефолт 10000 мс). Значение можно переопределить только облачным конфигом
(`remoteRulesStar.json` / `/data/staros/localOverrideStar.json`) — через
LAN-протокол оно не выставляется. Официальная справка SberDevices описывает
выключение именно так: «Пауза или Стоп, затем подождите 10 секунд».

## Замеры на живых колонках (3 колонки, треки Звука)

| действие | время от паузы до `mode = NONE` у всех |
| --- | --- |
| пауза на всех колонках | 12.8 с (повтор: 14.5 с) |
| пауза только ведомых | 11.3–11.5 с |
| пауза только мастера | 14.0 с |
| пауза мастера + повторная пауза через 6 с | 11.7 с |

Звук реально замолкает через 1.5–2 с после паузы; `NONE` приходит позже —
это исключительно таймер прошивки. Разброс ±3 с зависит от колонки:
SberBoom и SberPortal уходят раньше, Mini 2 иногда позже.

Вывод: физически ускорить роспуск группы из LAN нельзя. Можно убрать только
нашу собственную задержку.

## Что сделано в проекте

1. **Ответ `/api/multiroom/native/stop` возвращается сразу** (≈10 мс):
   пауза уходит всем участникам группы, состояние становится `stopping`
   с оценкой `dissolveAt`. Роспуск дожидается в фоне (`nativeStopTask`).
2. **Опрос ролей каждые 400 мс** вместо 700 мс — блокировка снимается в тот
   же момент, когда прошивка сообщила `NONE`.
3. **Обратный отсчёт в интерфейсе**: в панели «Все колонки» написано
   «группа распускается, осталось ~N с».
4. **Страховочная повторная пауза** только если за 15 с группа не исчезла
   (прошивка взводит таймер по команде, а не по факту тишины).
5. **Запуск звука и перемотка заблокированы** всё время, пока группа живёт:
   новый трек отменил бы роспуск, и колонки остались бы в мультируме.
   Сообщение теперь конкретное: «Мультирум ещё выходит из группы —
   попробуйте через N с».

## Как проверить самостоятельно

```bash
node diag/mr-timer.mjs           # тайминги роспуска: пауза мастера / всех / ведомых
node diag/mr-ab.mjs              # одиночная пауза против паузы + повтор
node diag/mr-command-scan.mjs    # перебор команд op=16: мгновенного стопа нет
node diag/mr-star-stop.mjs       # StarCommand 140 stop_multiroom — игнорируется
```
